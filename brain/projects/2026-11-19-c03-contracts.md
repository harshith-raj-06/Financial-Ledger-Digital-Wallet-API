## Proposed v0.1 signatures

- transaction(*, write=True) -> context manager yielding sqlite3.Connection.
- post_transaction(connection, request: PostingRequest) -> PostedTransaction.
- run_idempotent(connection, request: IdempotencyRequest, operation) -> OperationResult.
- Clock.now() -> timezone-aware UTC datetime.
- IdProvider.new_id() -> UUID v4 (API transport serializes IDs as strings).

PostingRequest names the type, debit and credit wallet IDs, one positive integer
minor-unit amount, currency, optional description and original reversal ID.
PostedTransaction carries the transaction ID and server time. Idempotency
context carries caller, operation, key, URL target and body; OperationResult
carries response status/body, transaction ID and replay state.

These DTOs describe interfaces; they do not implement money validation or
idempotency. Frozen dataclasses protect field assignment; Mapping-valued
payloads are treated as read-only by consumers, not deeply frozen.

Compatibility check: A's actual 001 branch uses integer ledger-entry row IDs.
The posting result does not prescribe an entry-ID representation, avoiding a
conflicting UUID assumption. Public cursor/entry-ID details remain an explicit
API-contract review point; A's migration is not changed by C03.

## Ownership and transaction discipline

A implements the real SQLite provider with required WAL/FULL/FK/busy settings.
C defines posting and the clock/ID interfaces. B implements real idempotency.
The API enters the transaction context; posting and idempotency never commit or
roll back. The operation callback closes over that same active connection.

The in-memory SQLite provider is a test double, not A/H03. It proves caller
commit/rollback and forbids writes in a read context. Fake posting records calls
and returns a deterministic result. Fake idempotency passes through, supplies a
preconfigured replay or raises a configured failure; it has no key storage,
validation, canonical hashing or deduplication logic.
